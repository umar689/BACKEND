1. CI/CD kya hai aur kyun zaroori hai

CI/CD ek automatic assembly line hai: developer code push karta hai, aur machine khud use test karke, build karke, server tak pahuncha deti hai. Insaan sirf faisla leta hai, haath ka kaam machine karti hai.

CI = Continuous Integration. Har developer ka code din mein kai baar main codebase mein milaya (integrate) jaata hai, aur har baar automatic tests chalte hain. Galti usi waqt pakdi jaati hai, hafte baad nahi.

CD = Continuous Delivery / Deployment. Jo code tests pass kar gaya, wo automatic tareeke se server tak pahunchaya jaata hai.

Ek analogy: chai ki factory

Socho tumhari chai ki factory hai. Bina machine ke, har packet haath se bharte ho, haath se tolte ho, haath se seal karte ho. Thak gaye toh galti hogi: kabhi kam chai, kabhi seal khula. CI/CD wo conveyor belt hai jisme har packet automatic tola jaata hai (tests), galat packet belt se hata diya jaata hai (pipeline fail), aur sahi packet seedha truck mein (deploy).

Test gate hai: fail hua toh code aage nahi badhta aur developer ke paas wapas jaata hai.

Bina CI/CD vs CI/CD ke saath

Golden rule: Deploy ek bore karne wali, roz ki cheez honi chahiye. Agar deploy karne mein darr lagta hai, toh pipeline mein kuch missing hai.

2. CI vs Continuous Delivery vs Continuous Deployment

Teeno mein farak sirf ek baat ka hai: production pe last button kaun dabata hai, insaan ya machine.

Bhara hua hissa machine karti hai, dashed hissa insaan.

LevelKya automatic haiProduction deployKab use karein
Continuous IntegrationBuild + tests har push peManual (pipeline nahi karti)Shuruaat, sabse pehla kadam
Continuous DeliveryBuild + test + dev/staging deployEk click / approval seZyada tar teams (hamara setup yahi hai)
Continuous DeploymentSab kuch, production bhiBina insaan ke, tests pass hote hiStrong test coverage + monitoring wali teams

Hamara setup Continuous Delivery hai: dev server pe sab automatic, production pe ek approval ke baad. Jab tests aur monitoring pe bharosa ho jaaye, approval hata ke Continuous Deployment pe ja sakte ho.

4. Git branching strategy

Pipeline branch dekh ke decide karti hai ki code kahan jayega, isliye branch ka naam hi deploy ka address hai: develop matlab dev server, main matlab production.

Har gol nishaan ek commit hai. develop mein merge hote hi dev server update hota hai, main mein merge hote hi (approval ke baad) production.

BranchKis kaam kiKahan deployKaun push kar sakta hai
feature/login-otpEk naya feature ya fixKahin nahi (sirf tests)Developer khud
developSab features yahan milte hainDev server, automaticSirf PR se merge
mainJo production pe chal raha haiProduction, approval ke baadSirf develop se PR
hotfix/payment-crashProd pe urgent fixmain se banta hai, main + develop dono mein mergeSenior dev

Roz ka kaam, step by step

  1. develop se nayi branch banao:

    git checkout develop && git pull
git checkout -b feature/login-otp

  2. Code likho, chhote-chhote commits karo:

    git add . && git commit -m "feat: OTP login API"
git push -u origin feature/login-otp

  3. GitHub pe feature/login-otp → develop ka Pull Request (PR) kholo. Pipeline tests chalayegi.

  4. Koi teammate code review kare. Tests green + review OK hone pe merge karo.

  5. Merge hote hi dev server pe automatic deploy. Wahan test karo.

  6. Release ke time develop → main PR banao, approve karo, production deploy.

Branch protection (zaroor lagao)

Repo → Settings → Branches → Add rule, main aur develop dono ke liye:

  • Require a pull request before merging (direct push band)

  • Require approvals: 1

  • Require status checks to pass: Install, lint, test, build job select karo

  • Do not allow bypassing the above settings

Iske bina koi bhi galti se seedha main pe push kar dega aur production toot jayega.

Commit message convention

feat: naya feature · fix: bug fix · chore: maintenance · docs: documentation · refactor: code saaf kiya, behaviour same · test: tests. Isse history padhna aur changelog banana aasaan ho jaata hai.

5. Environments: local, dev, staging, prod

Environment ek alag duniya hai jahan code chalta hai. Har duniya ka apna server, apna DB aur apni .env hoti hai. Code sab jagah same jaata hai, sirf config alag hota hai.

EnvironmentKaun use karta haiDataHamare paas
LocalDeveloper apne laptop peFake / seed dataHaan
DevelopmentTeam, QA, testingTest dataHaan (dev server)
StagingFinal check, prod jaisa hiProd jaisa (masked)Abhi nahi, baad mein add kar sakte ho
ProductionAsli usersAsli dataHaan

DB har environment ka alag kyun?

  • Dev pe galat migration ya DELETE chal gaya toh prod ka data safe rehta hai.

  • Testing ke kachre wale records asli users ko nahi dikhte.

  • Prod ke customers ka personal data developers ke haath nahi lagta.

Config: code ek, .env alag

Code mein kabhi password ya server ka address hardcode mat karo. Sab .env se padho:

  user: process.env.DB_USER,

DB_NAME=myapp_dev

# prod server ki .env
NODE_ENV=production

.env ko .gitignore mein daalo. Repo mein sirf ek .env.example rakho jisme keys hon, values nahi. Isse naya developer jaan jaata hai ki kaunsi settings chahiye.

6. GitHub Actions ki anatomy

GitHub Actions ek YAML file padhta hai: kab chalna hai (on), kya chalana hai (jobs), aur kis order mein (needs). Repo ke .github/workflows/ folder mein jo bhi .yml file hogi, GitHub use apne aap pipeline maan lega.

Sabse chhota workflow

name: Hello CI            # Actions tab mein ye naam dikhega
on: push                  # kisi bhi branch pe push hone pe chalo
jobs:
  hello:                  # job ka id
    runs-on: ubuntu-latest  # GitHub ki free Linux machine
    steps:
      - uses: actions/checkout@v4   # repo ka code machine pe laao
      - run: echo "Namaste CI!"     # koi bhi shell command

Ise push karo, GitHub → Actions tab kholo, aur pehli pipeline chalti dikhegi.

Jobs: parallel ya ek ke baad ek?

By default saari jobs ek saath (parallel) chalti hain, har ek apni alag fresh machine pe. needs lagane se order banta hai. Isliye deploy mein needs: test hai: test fail hua toh deploy chalega hi nahi.

Alag machine ka matlab: ek job mein install kiya node_modules doosri job mein nahi milega. Files share karni hon toh actions/upload-artifact aur actions/download-artifact use karo.

7. Hamari pipeline: Node + MySQL + GitHub + AWS EC2

Poora system 4 jagah pe chalta hai: developer ka laptop, GitHub (code + Actions), dev EC2 aur prod EC2. GitHub Actions dono servers mein SSH se ghus ke deploy.sh chalata hai, aur servers GitHub se code pull karte hain.

Developer sirf GitHub tak push karta hai; servers tak pahunchne ka kaam sirf runner ka hai, aur prod tak sirf approval ke baad.

Poori deploy.yml

name: CI/CD

on:
  push:
    branches: [develop, main]
  pull_request:
    branches: [develop, main]
  workflow_dispatch:

concurrency:
  group: deploy-${{ github.ref_name }}
  cancel-in-progress: false

jobs:
  test:
    name: Install, lint, test, build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm run lint --if-present
      - run: npm test --if-present
      - run: npm run build --if-present

  deploy:
    name: Deploy to ${{ github.ref_name == 'main' && 'production' || 'development' }}
    needs: test
    if: github.event_name != 'pull_request'
    runs-on: ubuntu-latest
    environment: ${{ github.ref_name == 'main' && 'production' || 'development' }}
    steps:
      - name: Deploy on server via SSH
        uses: appleboy/ssh-action@v1
        env:
          DEPLOY_ENV: ${{ github.ref_name == 'main' && 'production' || 'development' }}
          BRANCH: ${{ github.ref_name }}
          SHA: ${{ github.sha }}
          APP_DIR: ${{ vars.APP_DIR }}
          PM2_APP: ${{ vars.PM2_APP }}
          HEALTH_URL: ${{ vars.HEALTH_URL }}
          DB_NAME: ${{ vars.DB_NAME }}
        with:
          host: ${{ secrets.SSH_HOST }}
          username: ${{ secrets.SSH_USER }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          port: 22
          command_timeout: 20m
          envs: DEPLOY_ENV,BRANCH,SHA,APP_DIR,PM2_APP,HEALTH_URL,DB_NAME
          script: |
            set -e
            cd "$APP_DIR"
            git fetch --prune origin "$BRANCH"
            git show "$SHA:scripts/deploy.sh" > /tmp/deploy-$PM2_APP.sh
            bash /tmp/deploy-$PM2_APP.sh

8. deploy.sh: server pe kya hota hai

deploy.sh server pe 6 kaam karti hai: backup, code update, install, migrate, restart, health check. Inmein se koi bhi fail hua toh rollback() code ko pichhle commit pe le aata hai.

Laal dashed raasta kisi bhi step ke fail hone pe chalta hai; health check fail hone pe bhi wahi rollback().

Ek baarik baat: backup hi fail ho jaaye toh rollback ki zaroorat nahi padti, kyunki tab tak code badla hi nahi hota. Script wahin ruk jaati hai aur purana version chalta rehta hai.

Bash ki 4 zaroori cheezein

CodeMatlabIske bina kya hota
set -eKoi bhi command fail ho toh script ruk jaayenpm ci fail hone ke baad bhi restart ho jaata
set -uUndefined variable use hua toh errorcd $APP_DIRR (typo) chupchaap galat jagah chalta
set -o pipefaila | b mein a fail hua toh bhi errormysqldump fail, phir bhi khaali backup file ban jaati
set -E + trap ... ERRError aate hi ek function chalaoRollback kabhi automatic nahi hota

Step-by-step

Step 0: Zaroori values check

: "${APP_DIR:?APP_DIR missing}"

Agar APP_DIR khaali hai toh script wahin ruk jaati hai aur message dikhaati hai. Galat folder mein git reset --hard chal jaana bahut bura hota.

Step 1: Purana commit yaad rakho

PREV_SHA="$(git rev-parse HEAD)"

Rollback ko pata hona chahiye ki wapas kahan jaana hai.

Step 2: DB backup (sirf production)

mysqldump --single-transaction --routines --triggers --no-tablespaces "$DB_NAME" | gzip > "$BACKUP_FILE"
FlagKyun
--single-transactionInnoDB tables ko lock kiye bina consistent snapshot; site chalti rehti hai
--routines --triggersStored procedures aur triggers bhi backup mein
--no-tablespacesRDS / MySQL 8 pe PROCESS privilege ke bina error na aaye
| gzipBackup 5-10x chhota

Password command mein nahi, ~/.my.cnf file se aata hai, taaki ps command ya logs mein na dikhe. Last 10 backups rakhe jaate hain, purane delete.

Step 3: Rollback trap lagao

rollback() { ... git reset --hard "$PREV_SHA"; npm ci; pm2 reload ...; }
trap 'rollback; exit 1' ERR

Iske baad koi bhi command fail hui toh rollback apne aap chalega.

Step 4: Code update

git reset --hard "$SHA"

git pull ki jagah exact commit pe jaate hain. Server pe kisi ne file haath se badli ho toh bhi wo hat jaayegi, aur server hamesha wahi code chalayega jo GitHub pe test hua.

Step 5: Install + build

npm ci
npm run build --if-present

Step 6: Migrations

npm run migrate --if-present

Naye schema changes DB pe lagte hain. Ye npm prune se pehle hai kyunki sequelize-cli jaise tools aksar devDependency hote hain.

Step 7: devDependencies hatao

npm prune --omit=dev

Server pe sirf wahi packages rahein jo production mein chahiye. Kam disk, kam security risk.

Step 8: Zero-downtime restart

pm2 reload "$PM2_APP" --update-env

restart sab process ek saath maarta hai (kuch second site down). reload ek-ek karke naye process chalu karta hai, purane tab band hote hain jab naye ready hon. Ye cluster mode (pm2 start app.js -i max) mein poora zero-downtime hota hai.

Step 9: Health check

for _ in {1..10}; do curl -fsS -o /dev/null "$HEALTH_URL" && return 0; sleep 3; done

30 second tak har 3 second mein app se poochta hai "zinda ho?". Jawab nahi aaya toh rollback. App mein ek chhota route banao:

app.get('/health', async (req, res) => {
  try {
    await pool.query('SELECT 1');   // DB bhi check
    res.json({ status: 'ok' });
  } catch (e) {
    res.status(500).json({ status: 'db-down' });
  }
});

9. SSH aur keys

SSH key ek taala-chaabi ki jodi hai: public key taala hai (jise server pe laga do, kisi ko dikh jaaye koi dikkat nahi), private key chaabi hai (jo sirf login karne wale ke paas rehti hai). Server pe jo taala laga hai, sirf uski chaabi wala andar aa sakta hai. Password ki zaroorat hi nahi.

Arrow us taraf hai jidhar login hota hai: chaabi wala, taale wale ke paas jaata hai.

Hamare setup mein 2 jodiyaan

JodiTaala (public) kahanChaabi (private) kahanKaam
gha_deployDono servers ki ~/.ssh/authorized_keysGitHub secret SSH_PRIVATE_KEYGitHub Actions server mein login kare
github_deploy (har server ki alag)GitHub repo → Deploy keysServer ki ~/.ssh/github_deployServer GitHub se git fetch kare

Key 1 banana (laptop pe, ek baar)

ssh-keygen -t ed25519 -C "github-actions" -f gha_deploy -N ""
FlagMatlab
-t ed25519Modern, chhoti aur fast key type (RSA se behtar)
-C "github-actions"Comment, bas pehchaan ke liye
-f gha_deployFile ka naam
-N ""Passphrase khaali (pipeline password type nahi kar sakti)

Public key dono servers pe:

mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo "<gha_deploy.pub ka content>" >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

Private key (gha_deploy, BEGIN se END tak poora) GitHub → Settings → Environments → har environment → secret SSH_PRIVATE_KEY.

Key 2 banana (har server pe)

ssh-keygen -t ed25519 -C "prod-server" -f ~/.ssh/github_deploy -N ""
cat ~/.ssh/github_deploy.pub     # ye GitHub → Deploy keys mein, read-only
printf 'Host github.com\n  IdentityFile ~/.ssh/github_deploy\n' >> ~/.ssh/config
chmod 600 ~/.ssh/config
ssh -T git@github.com            # "successfully authenticated" aana chahiye

Permissions kyun itni strict?

SSH bahut shakki hai: agar ~/.ssh ya authorized_keys doosre users bhi padh/likh sakte hain, toh SSH key ko ignore kar deta hai aur Permission denied (publickey) deta hai. Isliye 700 folder ke liye aur 600 files ke liye.

Port 22 aur GitHub runners

GitHub ke runners ke IP har baar badalte hain, isliye EC2 Security Group mein port 22 sabke liye (0.0.0.0/0) kholna padta hai. Isse safe rakhne ke liye server pe password login band karo (/etc/ssh/sshd_config mein PasswordAuthentication no). Aur zyada safe tareeka (bina port 22 khole) section 17 mein hai: AWS SSM.

10. Database migrations

Migration DB ke liye git jaisa hai: har schema change ek numbered file hai, jo code ke saath commit hoti hai aur har DB pe ek hi order mein, sirf ek baar chalti hai. Isi se dev aur prod ka schema hamesha same level pe rehta hai.

Migration kaise kaam karti hai

Har DB mein ek chhoti table hoti hai (SequelizeMeta, knex_migrations ya _prisma_migrations) jisme likha hota hai ki kaunsi migration files chal chuki hain. npm run migrate sirf wo files chalata hai jo is list mein nahi hain.

Ek migration ka example (Knex)

// migrations/20261103_add_phone_to_users.js
exports.up = (knex) =>
  knex.schema.alterTable('users', (t) => {
    t.string('phone', 15).nullable();
  });

exports.down = (knex) =>
  knex.schema.alterTable('users', (t) => {
    t.dropColumn('phone');
  });

up = change lagao, down = change wapas lo.

Baseline: purane DB ko migrations pe laana

Hamare dono DB pehle se bane hue hain aur same level pe hain. Inhe migrations pe laane ke liye:

  1. Current schema ko ek pehli migration (001_baseline) mein likho, jaisa DB abhi hai.

  2. Is migration ko kisi DB pe chalao mat. Bas dono DB ki tracking table mein entry daal do ki ye chal chuki hai.

  3. Naye DB (jaise kisi developer ka local) pe ye migration poora schema bana degi.

  4. Iske baad har change nayi migration file se.

Golden rules

  • Chal chuki migration file ko kabhi edit mat karo. Galti hui toh nayi migration likho jo use theek kare.

  • Prod pe kabhi haath se ALTER TABLE mat chalao. Ek baar kiya toh dev aur prod ka schema alag ho jaayega.

  • Badi tables (lakhon rows) pe index ya column add karne se table lock ho sakti hai; pehle dev pe utne data ke saath time dekho.

Expand-contract: column rename bina downtime

Seedha RENAME COLUMN name TO full_name karoge toh deploy ke beech ke kuch second mein purana code name dhundhega aur crash hoga. Aur rollback karne pe bhi purana code tootega. Isliye 3 deploy mein karo:

DeployMigrationCodeRollback safe?
1. Expandfull_name column addDono columns mein likho, name se padhoHaan, purana code name use karta hai
2. MigratePurana data copy: UPDATE users SET full_name = namefull_name se padhoHaan, name abhi bhi hai
3. Contractname column dropSirf full_nameHaan, ab koi name use nahi karta

Yahi pattern column delete, type change, aur table split pe bhi lagta hai: pehle naya add karo, phir purana hatao, kabhi ek saath nahi.

Fork se aaye PR ka khatra

Public repo mein koi bhi fork karke PR bhej sakta hai. Agar wo PR secrets ke saath chal gaya toh wo deploy.yml badal ke secrets chura sakta hai. GitHub by default fork ke PR ko secrets nahi deta. Isliye pull_request_target trigger tab tak use mat karo jab tak iska khatra poori tarah na samjho.

Workflow mein permissions

permissions:
  contents: read   # code padh sakta hai, likh nahi sakta

Ise deploy.yml mein on: ke neeche daal do. Hamari pipeline ko repo mein kuch likhna nahi hai, toh read kaafi hai.

12. Backup, rollback aur disaster recovery

Rollback ke do hisse hain, code aur data. Code wapas lana aasaan aur safe hai; data wapas lana mushkil hai kyunki backup ke baad aaye naye orders ya users bhi chale jaate hain.

Kya galat hua, kya karna hai

SituationKya karoData loss?
Health check failKuch nahi, deploy.sh khud code rollback kar deti haiNahi
Deploy ho gaya, baad mein bug milaGit mein revert commit, main pe merge, pipeline naya deploy karegiNahi
Bahut urgent, pipeline ka wait nahiServer pe manual code rollback (neeche)Nahi
Migration ne data bigaad diyaPehle fix-forward migration socho; last option backup restoreHaan, backup ke baad ka
Server hi mar gayaNaya EC2, setup steps, latest backup restoreLast backup tak

Sabse achha rollback: git revert

git checkout main && git pull
git revert <kharab_commit_sha>
git push    # branch protection hai toh PR banao

Isse history saaf rehti hai aur deploy usi pipeline se hota hai jisse baaki sab.

Manual code rollback (emergency)

cd /var/www/app
git log --oneline -5
git reset --hard <purana_sha>
npm ci && npm prune --omit=dev
pm2 reload myapp

Baad mein main mein bhi revert zaroor karna, warna agla deploy kharab code wapas le aayega.

DB restore

ls -lt ~/db-backups | head
# Pehle alag DB mein restore karke check karo:
mysql -e "CREATE DATABASE restore_check"
gunzip < ~/db-backups/myapp_prod_20261103_221500_ab12cd3.sql.gz | mysql restore_check
# Sab theek laga toh asli DB pe (app band karke):
pm2 stop myapp
gunzip < ~/db-backups/<file>.sql.gz | mysql myapp_prod
pm2 start myapp

3-2-1 backup rule

Deploy wala backup usi server pe hai. Server ki disk gayi toh backup bhi gaya. Isliye:

  • 3 copies data ki

  • 2 alag tarah ki jagah (server disk + S3)

  • 1 copy doosri location / region mein

Roz raat ka backup S3 mein bhejo:

# crontab -e, roz raat 2 baje
0 2 * * * mysqldump --single-transaction --no-tablespaces myapp_prod | gzip | aws s3 cp - s3://myapp-backups/daily/$(date +\%F).sql.gz

RDS use karte ho toh automated backups aur point-in-time recovery console se on kar do.

Backup tabhi backup hai jab restore karke dekha ho. Mahine mein ek baar kisi backup ko test DB mein restore karke check karo.

13. Deployment strategies

Naya version users tak kaise pahunche, iske 5 tareeke hain. Hamara setup rolling hai (pm2 reload ek-ek process badalta hai). Jaise app bada ho, blue-green ya canary pe ja sakte ho.

StrategyKaise kaam karti haiDowntimeRollback speedKharchaKab use karein
RecreateSab band, naya chaluHaan, kuch secondDheema (dobara deploy)Sabse kamChhote internal tools
RollingEk-ek instance/process badloNahiMediumKamZyada tar apps (hamara setup)
Blue-greenDo poore environment; traffic ek jhatke mein naye peNahiTurant (traffic wapas)2x serversJahan rollback seconds mein chahiye
CanaryPehle 5% users naye pe, sab theek toh 25%, 50%, 100%NahiTurant (5% hi affected)Medium + monitoringBade user base wale apps
Feature flagsCode deploy ho jaata hai par feature off; baad mein switch onNahiTurant (flag off)Flag systemBade features, A/B testing

Blue-green mein rollback matlab traffic wapas purane pe; canary mein galti sirf 5% users tak rehti hai.

Blue-green AWS pe kaise dikhta hai

Do EC2 (ya do Auto Scaling groups) ek Application Load Balancer ke peeche. Blue pe purana version chal raha hai. Green pe naya deploy karo, test karo, phir ALB ka target group Blue se Green pe switch. Gadbad hui toh wapas Blue pe switch, bas.

Feature flag ka simple example

// .env: FEATURE_NEW_CHECKOUT=false
if (process.env.FEATURE_NEW_CHECKOUT === 'true') {
  return newCheckout(req, res);
}
return oldCheckout(req, res);

Code prod pe pahunch gaya, par users ko tab dikhega jab flag true hoga. Isse "deploy" aur "release" alag ho jaate hain.

14. CI mein testing

Pipeline utni hi achhi hai jitne uske tests. Tests nahi hain toh pipeline bas "tez tareeke se bug deploy karne ki machine" hai.

Test pyramid

IntegrationAPI + asli DB saath meinMedium (20%)SecondsJest + Supertest + MySQL container
End-to-end (E2E)Browser mein poora user flowKam (10%)MinutesPlaywright, Cypress

Neeche wide (bahut saare tez unit tests), upar patla (kuch dheeme E2E tests). Ulta pyramid matlab slow aur toot-ne wali pipeline.

Unit test example

// utils/price.js
exports.withGst = (amount) => Math.round(amount * 1.18 * 100) / 100;

// utils/price.test.js
const { withGst } = require('./price');
test('18% GST lagta hai', () => {
  expect(withGst(100)).toBe(118);
});

Asli MySQL ke saath integration tests in CI

GitHub Actions job ke saath ek MySQL container chala sakta hai (services). Test khatam, container khatam. Prod ya dev DB ko chhoona bhi nahi padta.

  test:
    runs-on: ubuntu-latest
    services:
      mysql:
        image: mysql:8.0
        env:
          MYSQL_ROOT_PASSWORD: root
          MYSQL_DATABASE: myapp_test
        ports: ['3306:3306']
        options: >-
          --health-cmd="mysqladmin ping -proot"
          --health-interval=5s --health-timeout=3s --health-retries=10
    env:
      DB_HOST: 127.0.0.1
      DB_USER: root
      DB_PASSWORD: root
      DB_NAME: myapp_test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, cache: npm }
      - run: npm ci
      - run: npm run migrate      # khaali test DB pe saari migrations
      - run: npm test

Bonus fayda: har PR pe migrations ek khaali DB pe shuru se chalti hain, toh tooti migration prod tak pahunchne se pehle pakdi jaati hai.

Deploy ki notification

Team ko pata hona chahiye ki kab kya deploy hua. deploy job ke end mein Slack / Discord webhook:

Matrix build

  test:
    strategy:
      matrix:
        node: [20, 22]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '${{ matrix.node }}', cache: npm }
      - run: npm ci && npm test

Ek job do baar chalegi, parallel mein, har Node version pe.

Docker: "build once, run anywhere"

Abhi har server pe npm ci alag chalta hai. Docker mein CI ek baar image banata hai, aur wahi exact image dev aur prod dono pe chalti hai.

FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY . .
EXPOSE 3000
CMD ["node", "src/index.js"]

Flow: CI image build → Amazon ECR mein push (tag = commit SHA) → server pe docker pull + restart, ya seedha ECS pe deploy. Rollback matlab purane SHA ka image chala do.

OIDC: GitHub mein AWS keys ki zaroorat khatam

AWS CLI use karna ho (S3, ECR, ECS) toh purana tareeka tha AWS_ACCESS_KEY_ID secret mein rakhna, jo kabhi expire nahi hota. OIDC mein GitHub har run ke liye AWS se ek temporary token leta hai jo kuch minute mein khatam ho jaata hai.

permissions:
  id-token: write
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: arn:aws:iam::123456789012:role/github-deploy
      aws-region: ap-south-1

AWS IAM mein ek role banta hai jo sirf tumhare repo aur main branch pe bharosa karta hai.

AWS SSM: bina port 22 ke deploy

EC2 pe SSM Agent (Ubuntu / Amazon Linux mein pehle se hota hai) + IAM role lagao. Phir OIDC ke saath:

aws ssm send-command \
  --instance-ids i-0abc123 \
  --document-name AWS-RunShellScript \
  --parameters 'commands=["sudo -u ubuntu bash /var/www/app/scripts/deploy.sh"]'

Port 22 Security Group se poori tarah band kar sakte ho, aur har command AWS CloudTrail mein log hoti hai.

Infrastructure as Code

EC2, Security Group, RDS, IAM roles sab ek code file mein (Terraform ya AWS CDK). Server bigad gaya toh terraform apply se 10 minute mein naya. Infrastructure ke changes bhi PR + review se hote hain, bilkul app code ki tarah.

Preview environments

Har PR ke liye ek temporary environment (pr-42.dev.myapp.com) jo PR band hote hi delete ho jaata hai. Docker + ECS ya Vercel / Render jaise platforms ke saath sabse aasaan banta hai.

18. Setup checklist, practice aur roadmap

Ye checklist upar se neeche tick karte jao; sab tick hone pe tumhari pipeline production-ready hai.

Setup checklist

Repo

  • .github/workflows/deploy.yml aur scripts/deploy.sh commit kiye

  • package-lock.json commit hai

  • package.json mein migrate script hai; default test script hatayi ya asli tests likhe

  • .env .gitignore mein hai, .env.example repo mein hai

  • App mein /health route hai

  • develop branch bani hai

Dono servers (dev + prod)

  • Node 22, git, mysql-client, PM2 install

  • gha_deploy.pub ~/.ssh/authorized_keys mein

  • Server ki apni deploy key GitHub → Deploy keys mein; ssh -T git@github.com OK

  • Repo /var/www/app mein clone, sahi branch pe

  • .env bani hai

  • App ek baar pm2 start ... --name myapp, phir pm2 save aur pm2 startup

  • Security Group mein port 22 khula, password login band

Sirf prod server

  • ~/.my.cnf ([mysqldump] section mein host, user, password), chmod 600

  • mysqldump --no-tablespaces myapp_prod | head chal raha hai

GitHub

  • Environments development aur production bane

  • Har environment mein secrets: SSH_HOST, SSH_USER, SSH_PRIVATE_KEY

  • Har environment mein variables: APP_DIR, PM2_APP, HEALTH_URL; prod mein DB_NAME

  • Production: Required reviewers + Deployment branches = main

  • Branch protection main aur develop pe

DB

  • Baseline migration bani, dono DB mein "already applied" mark

  • Ek test migration dev pe chal ke prod tak pahunchi

Practice exercises (aasaan se mushkil)

  1. Sirf echo wala "Hello CI" workflow banao aur Actions tab mein chalta dekho.

  2. Jaan-boojh ke ek test fail karo, push karo. Dekho deploy job skip hoti hai.

  3. develop pe ek chhota text change push karo, dev server pe dikhna chahiye.

  4. Nayi migration likho (users mein phone column), dev pe chalao, phir main tak le jao.

  5. /health ko jaan-boojh ke 500 return karwao, dev pe deploy karo, auto rollback dekho.

  6. Prod ke latest backup ko ek restore_check DB mein restore karke dekho.

  7. Workflow mein MySQL services container wale integration tests jodo.

  8. Slack / Discord notification jodo.

  9. node: [20, 22] matrix lagao.

  10. App ko Docker mein daalo aur image ECR mein push karo.
